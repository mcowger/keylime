# Release checklist

Keylime is an incompatible hard fork. Its package is `@mcowger/keylime`, and
its runner uses the pinned omp integration build rather than a stock `omp`.
Upstream packages and release URLs do not publish this fork's changes.
All GitHub Actions workflows are disabled; pushing a tag does not start a build
or publish a release. Do not re-enable them as part of local verification.

## Local release verification

From the intended checkout, install the pinned Bun runtime and dependencies.
Root `bun install --frozen-lockfile` also installs the integration packages pinned
in `runner/omp-build.json`. Make sure `unzip` is available before running it:

```bash
mise trust
mise install
bun install --frozen-lockfile
```

Update API source schemas, semantics and annotations when behavior changes,
regenerate and commit the API documents, and run the local release checks
before delivery:

```bash
# Run bun run api separately when maintaining API documentation.
bun run release:check
```

`release:check` includes formatting, typechecking, tests, the production build and
smoke checks. `bun run smoke` builds the runner first. API documentation generation
is explicit and does not gate development, builds or deployments; releases include
the checked-in documents, which may be stale.

Release publication is not automated by this repository. Verify any publication
procedure and destination separately; inherited upstream release settings are not
instructions for publishing Keylime.

## Building binary archives

After installing the root dependencies, run:

```bash
bun run build:binary
```

This builds the browser assets and runners, then builds the four Keylime
archives in parallel for Linux and macOS, on x64 and arm64. No prebuilt runner
is required. The archives and unpacked directories are written under `release/`.
Each directory contains `keylime`, `keylime-omp`, browser assets, API documents
and licenses. Keep the directory contents together when installing it.

Use `--target bun-linux-x64-baseline` (or another Bun target) to build one
platform. `--no-archive` leaves just the unpacked output. `--no-runner` omits
the runner from each archive but still builds it under `runner/release/` so it
can be attached separately to the matching release.

Build the standalone terminal client for the current platform with
`bun scripts/build-klc-binary.ts`. It writes `release/klc-<os>-<arch>.tar.gz`;
the archive contains `klc` and its licenses, not the server or browser assets.
The executable embeds Bun, so users don't need Bun installed. Pass `--with-klc`
to `bun run build:binary` to build the client alongside Keylime for each target.

## Runtime and upgrades

Keylime runs on Bun, not Next.js. The web server defaults to `127.0.0.1:30177`;
`keylime host` runs the host daemon separately. The `keylime systemd install`
and `keylime launchd install` commands register both services. Use the matching
`status` and `uninstall` commands to manage them together.

To install only the daemon and runner on a new machine, see [remote host deployment](remote-host-deployment.md).

Authentication is optional, including on non-loopback binds. Set a persistent
`KEYLIME_PASSWORD_HASH` generated by `keylime hash-password` when authentication
is needed. `--password` is rejected. Use HTTPS through a trusted reverse proxy
or VPN for remote access. A reverse proxy must forward WebSocket upgrades on
`/api/hosts/link` and `/api/events/link`.

For host-link upgrades, update the web server before its hosts. Hosts on an
older incompatible build report that they need an upgrade. Back up agent data
before changing versions; rollback is not a data-compatibility guarantee.

## Build identity in the UI

Click or tap the key lime logo to reveal the package version. If the build's
Git `HEAD` has no tag, the reveal also shows the full commit hash and the
committer date in `YYYY-MM-DD` format. Any tag pointing exactly at `HEAD`
keeps the version-only display; a tag on an ancestor does not.

Both the production build and development server resolve this metadata from
the source checkout, ignoring inherited repository-location overrides. Explicit
`safe.directory` trust from Git's configured files or `GIT_CONFIG_COUNT` is preserved.
The metadata is bundled into the client, including in npm packages and binary
releases; no Git command runs when a user clicks the logo.
Source archives without Git metadata keep the version-only display.

The development bootstrap initializes missing browser constants once. Empty
commit fields are valid, and later hot reloads keep the existing listener.
